# GL091 — Optional `needs:` entry on a deploy job

**Severity:** `warn`  
**OWASP:** [CICD-SEC-1 – Insufficient Flow Control Mechanisms](https://owasp.org/www-project-top-10-ci-cd-security-risks/CICD-SEC-01-Insufficient-Flow-Control-Mechanisms)  
**CWE:** [CWE-691 – Insufficient Control Flow Management](https://cwe.mitre.org/data/definitions/691.html)

## Risk

The long form of `needs:` accepts [`optional: true`](https://docs.gitlab.com/ci/yaml/#needsoptional): when the needed job does not exist in the pipeline, the needing job is created anyway instead of failing. A job is absent whenever its `rules:`/`only:`/`except:` do not create it — for example a security scan that runs on merge requests but not on a tag pipeline, or a gate excluded by a changed-files condition.

If a deploy job treats such a job as a prerequisite gate and marks it `optional: true`, the deploy **still runs in every pipeline where the gate job was never created**. The gate disappears silently rather than blocking the pipeline, which is the opposite of what a security gate must do: unlike a failing need, a missing optional need produces no failed pipeline status.

## What glsec checks

A `warn` is reported for every `needs:` mapping entry that sets `optional: true` (a YAML boolean or the string `"true"`) on a job that deploys:

- the job declares an `environment:` (its own or inherited through `extends:`), or
- the job runs in a stage named `deploy` (its own or inherited).

Each finding names the deploy job, the needed job (its `job:` value), and points at the `optional: true` line.

The following stay silent:

- a plain long-form need without `optional:`, or with `optional: false` — a missing job then fails the deploy, as a gate should;
- a string need (`needs: ["sast"]` / `- sast`) — the short form cannot carry `optional:`;
- a non-deploy job (no `environment:`, not in the `deploy` stage), including a job merely *named* "deploy" while it runs in another stage — optional needs are a legitimate pattern there;
- hidden template jobs (`.template`), which never run themselves.

## Trigger example

```yaml
stages: [test, deploy]

secret_detection:
  stage: test
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
  script: [./scan-secrets.sh]

deploy_prod:
  stage: deploy
  environment: production
  needs:
    - job: secret_detection
      optional: true
  script: [./deploy.sh]
```

On a tag or branch pipeline `secret_detection` is never created, and because the need is optional `deploy_prod` runs without it.

## Safe alternative

Make the gate a hard prerequisite by dropping `optional: true`. The deploy then fails if the gate job is absent, so the gate's `rules:` must be broad enough to create it in every pipeline the deploy can run in:

```yaml
stages: [test, deploy]

secret_detection:
  stage: test
  script: [./scan-secrets.sh]

deploy_prod:
  stage: deploy
  environment: production
  needs:
    - job: secret_detection
  script: [./deploy.sh]
```

The string form is required as well:

```yaml
deploy_prod:
  stage: deploy
  environment: production
  needs: [secret_detection]
  script: [./deploy.sh]
```

If the dependency is genuinely unrelated to gating the deploy (an optional notification or enrichment job), the finding can be suppressed with a reason:

```yaml
deploy_prod:
  stage: deploy
  environment: production
  needs:
    - job: secret_detection
    - job: notify_slack
      optional: true  # glsec:ignore GL091 -- notification only, not a security gate
  script: [./deploy.sh]
```
